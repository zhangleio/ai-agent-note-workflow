# Agent Note：清理已完成项命令

Status: rejected — 批量删除必须先具备归档、恢复或撤销语义，才能安全交付

[English](2026-08-24-clear-completed-command.md) | 中文

后续工作交付了[批量归档已完成待办](../../implemented/feature/2026-08-24-bulk-archive-completed.md)，它是可恢复的状态转换，而不是此处否决的永久 `clear` 操作。本否决结论保持不变。

## 问题

随着列表增长，逐个按标识符删除已完成待办会变得重复。批量操作比 `remove` 更具破坏性，因此其范围、确认机制和空结果行为需要明确的产品决策。

## 提案

增加 `clear --yes`。它删除所有已完成待办，保留每条开放待办及其标识符，并输出 `Cleared <count> completed todo(s).`。强制使用 `--yes` 标志，使批量删除意图明确，同时保持非交互脚本能力。

没有已完成待办时运行 `clear --yes` 会成功、报告零，并且不重写数据文档。不带 `--yes`、带位置参数或带不支持选项的 `clear` 会失败且不写入。其他命令会拒绝 `--yes`，而不是静默忽略。

该命令复用当前经过验证的 JSON 读取和临时文件替换。它不增加撤销历史、回收站文档或新存储格式。

## 考虑过的替代方案

**删除所有待办。** 完全重置容易描述，但可能破坏未完成工作。清理已完成项可以满足日常清理，而不扩展到数据库重置语义。

**不要求确认。** 命令名称表达了清理意图，但一次调用可以删除多条记录。要求 `--yes` 可以将批量删除与已接受的直接单项 `remove` 行为区分开。

**使用 `y/N` 交互提示。** 提示可以防止随意误操作，但会使自动化、重定向输入、取消和测试更复杂。显式标志提供确定性确认。

**没有可清理内容时报错。** 没有匹配记录不是无效请求。将其视为成功，可让计划清理和重复清理保持幂等。

**将已完成待办移入回收站或归档文件。** 这样可以恢复，但会引入另一个持久文档、保留策略、恢复命令和一致性行为。这些能力需要独立的持久化提案。

**继续重复使用 `remove`。** 现有功能可以得到相同最终状态，但调用方必须先解析 `list`、识别已完成记录并执行多次写入。CLI 拥有完成状态，可以在当前文档粒度上原子执行该操作。

## 验收标准

- `clear --yes` 删除所有已完成待办，并保留开放待办且不重新编号。
- 命令报告删除数量，并使用正确的单复数措辞。
- 没有已完成待办时，报告零，并保持现有文档逐字节不变。
- 缺少 `--yes`、出现意外位置参数、不支持选项，或者在其他命令上使用 `--yes` 时，都会失败且不写入。
- 聚焦测试覆盖混合状态、空匹配状态、缺少确认和选项所有权。
- 本 Note 移入 `implemented/` 前，`npm run check` 必须通过。

## 风险

批量删除没有应用级撤销。确认只能证明调用方提供了标志，不能证明调用方审阅了每条匹配待办。该操作继承现有的全量文档重写和并发写入者限制。
