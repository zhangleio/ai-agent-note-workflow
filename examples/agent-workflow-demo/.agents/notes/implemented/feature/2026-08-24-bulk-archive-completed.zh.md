# Agent Note：批量归档已完成待办

Status: implemented

[English](2026-08-24-bulk-archive-completed.md) | 中文

## 问题

归档已完成待办需要重复执行单项归档命令。早先的[清理已完成项提案](../../rejected/feature/2026-08-24-clear-completed-command.md)因批量删除没有归档、恢复或撤销语义而被拒绝。[持久待办归档](../architecture/2026-08-24-durable-todo-archive.md)提供可恢复的归档状态和稳定标识符，使批量移动无需永久删除。

## 决策

CLI 提供 `archive --completed --yes`。它将所有已完成待办从 `active` 移到 `archived`，保留开放待办和全部标识符，并输出 `Archived N completed todo(s).`。布尔选项 `--completed` 和 `--yes` 可以按任意顺序出现。

这些选项选择独立的批量模式。同时提供标识符和任一选项会失败且不写入；单项 `archive <id>` 保持不变，也不接受这两个选项。除 `archive` 外的命令会拒绝这两个选项，而不是静默忽略。

即使归档待办可以恢复，`--yes` 仍是必需的。它记录调用方对多项状态转换的明确意图；恢复仍需逐项进行。

没有活跃的已完成待办时，命令成功，输出 `Archived 0 completed todo(s).`，并且不重写现有文档。非空转换通过现有临时文件替换只写入一次版本 1 文档。

## 考虑过的替代方案

**复用 `clear --yes`。** 旧名称暗示删除，并携带被拒绝提案的语义。`archive` 能准确表达可恢复操作。

**使用 `archive completed`。** 位置子命令容易解析，但所选选项形式将完成状态明确表达为筛选条件。该命令仍只拥有一个筛选器。

**不使用 `--yes`。** 恢复能力降低了误操作后果，但恢复许多项目需要重复命令。对于范围广泛的转换，明确确认仍然合适。

**交互式提示。** 提示会使自动化、重定向输入、取消和测试更复杂。必需的布尔标志是确定性的。

**同时接受标识符和 `--completed`。** 将其解释为状态检查或忽略一个输入会产生含糊的第三种模式。单项与批量归档互斥。

**零匹配时报错。** 没有匹配的已完成待办是有效稳定状态。成功返回使计划任务和重复清理具有幂等性。

**同时增加批量恢复。** 批量恢复需要筛选器或批次身份，仍属于独立功能决策。

## 验证

`npm run check` 验证五篇 Agent Note，编译严格 TypeScript 程序，并通过十七项 Node.js 测试。批量专项测试证明两种选项顺序、只移动已完成记录、保留开放与归档状态以及 `nextId`、准确计数输出、零匹配字节稳定性、拒绝不完整选项组合、拒绝 ID 与选项混用，以及拒绝其他命令使用这些选项。现有单项归档、归档列表和恢复测试继续通过。

## 后果

已完成工作可以在一次可恢复的文档转换中归档，而不会重新引入永久 `clear`。固定输出和顺序无关的选项支持脚本，明确确认则将范围广泛的操作与单项归档区分开。

确认只能证明调用方提供了 `--yes`，不能说明审阅了哪些记录。恢复仍然逐项进行，因此撤销大型批量归档较为繁琐。该操作继承版本 1 文档的全量重写和并发写入者限制。
