# Agent Note：持久待办归档

Status: implemented

[English](2026-08-24-durable-todo-archive.md) | 中文

## 问题

原始数组文档支持永久 `remove`，但无法恢复删除的待办。缺少恢复能力导致[批量清理](../../rejected/feature/2026-08-24-clear-completed-command.md)被拒绝。恢复还与已实施的“删除当前最大 ID 后可以复用标识符”决策冲突，因为恢复旧待办时可能与较新的活跃标识符碰撞。

## 决策

存储使用一个版本化文档，其中包含单调分配器以及活跃和归档集合：

```json
{
  "version": 1,
  "nextId": 4,
  "active": [],
  "archived": []
}
```

`nextId` 大于两个集合中的所有标识符，并且永不减小。`add` 消耗该值并递增，因此标识符在文档的完整历史中保持唯一。`list` 和 `done` 只操作 `active`。

`archive <id>` 将一条活跃待办移入 `archived`，`archive list` 按标识符顺序输出归档待办，`restore <id>` 将一条归档待办移回 `active`。这些转换保留标识符、文本、创建时间和完成状态。

旧 `remove` 命令被撤销。调用它会失败且不写入，并引导用户使用 `archive`；它既不是别名，也不是永久删除的逃生口。

### 旧格式迁移

读取器接受以前的顶层待办数组作为旧版本 0，并在内存中投影为 `{ version: 1, nextId: maxId + 1, active: legacyTodos, archived: [] }`。读取仍不修改数据。第一次成功的变更命令通过现有临时文件替换写入投影后的版本 1 文档。

畸形数组、重复或无效标识符、无效版本 1 文档以及不支持的版本都会失败且不替换文件。迁移保留每条现有待办的标识符和字段。

### 取代关系

本决策保留原 JSON CLI 的分层、验证和原子替换，同时改变数组文档和分配细节。它取代[删除待办命令](../../archived/feature/2026-08-24-remove-todo-command.md)记录的 ID 复用和永久删除行为；那篇冻结 Note 继续作为历史链接，而本 Note 是当前权威。

归档满足了被拒绝 clear 提案所要求的恢复前置条件，但不增加 `clear`。批量归档仍是独立的产品决策。

## 考虑过的替代方案

**为活跃和归档待办使用两个文件。** 移动待办需要在没有事务的情况下替换两个文件。崩溃可能导致项目在文档间重复或丢失。

**只实现一步撤销。** 撤销需要决定记录是否跨重启保留，以及第二个破坏性命令如何处理它。持久归档提供明确且可检查的状态。

**保留标识符复用，并在恢复冲突时重新编号。** 重新编号会破坏为恢复所选择的身份。单调分配器消除了碰撞。

**将 `remove` 保留为 `archive` 的别名。** 这会为同一操作留下两个名称，并保留具有误导性的永久删除承诺。针对性的迁移错误更加明确。

**在归档之外保留永久 `remove`。** 这会让调用方绕过恢复。永久清除需要独立的保留期和确认决策。

**拒绝旧数组。** 即使旧格式可以确定性迁移，这也会破坏首版数据的连续性。

**每次读取旧格式时都重写。** 这会让 `list` 意外修改用户数据。迁移只在已经请求的成功写入中发生。

## 验证

`npm run check` 验证四篇 Agent Note，编译严格 TypeScript 程序，并通过十四项 Node.js 测试。存储测试证明旧格式投影不修改数据、版本 1 往返、跨集合重复拒绝、不支持版本拒绝以及 `nextId` 验证。CLI 测试证明归档/恢复的可见性和状态保留、无效转换不修改数据、单调分配、首次写入迁移，以及不写入的 `remove` 迁移错误。

## 后果

删除的待办可以恢复，标识符在归档和恢复过程中保持稳定。活跃与归档状态在一次原子文档替换中移动，旧首版数据无需独立命令即可升级，读取时也不会修改。

版本化格式为未来存储变化建立了明确的迁移义务。文档仍然全量重写，也不防止并发进程冲突。归档数据会在没有清除操作的情况下持续增长。撤销 `remove` 是这个预发布演示中有意的命令兼容性破坏。
