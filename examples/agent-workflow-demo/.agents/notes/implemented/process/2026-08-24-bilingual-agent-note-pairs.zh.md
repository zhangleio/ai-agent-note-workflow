# Agent Note：双语 Agent Note 配对

Status: implemented

[English](2026-08-24-bilingual-agent-note-pairs.md) | 中文

## 问题

演示仓库目前只用英文保存 Agent Note。DeepSeek Harness 则将英文和简体中文视为同等权威，并要求每份活跃 Note 都是完整的三文件组：`topic.md`、`topic.zh.md` 和 `topic.i18n.yaml`。因此，这个演示遗漏了它本应讲解的一项重要工作流。

当前校验器按 Markdown 文件而非决策组计数，无法区分中文对侧文件和第二个主题，归档时也只冻结英文文件。如果仅增加翻译而不修改这些规则，验证会失败，或者生命周期与归档保证仍不完整。

## 决策

每份活跃 Agent Note 都是同目录三件套。英文和中文文件具有相同的状态、标题层级、事实、备选方案、链接和代码块，并在状态块后提供互相指向的语言切换行。两种语言没有主次之分。YAML 记录保存双方在最近一次人工确认语义一致时的 Git blob hash。

校验器以不带语言后缀的英文 Note 发现决策组。它要求中文对侧文件和一致性记录同时存在，检查双方当前 Git blob hash 与记录一致，验证两种语言中的生命周期状态与必需章节，检查双向语言链接和结构签名，拒绝孤立的配对文件，并报告 Note 组数量而不是 Markdown 文件数量。

生命周期变化必须同时移动三个文件。Proposed、implemented 和 rejected 配对只有在双方同步更新并刷新记录时才能继续编辑。只有完整且一致的三件套才允许归档；三个文件都要按各自格式接收或保留归档元数据，并由归档 manifest 冻结。

先前六份 Note 已在一次有界操作中完成双语化。已归档的 remove Note 只为补齐缺失的中文对侧、一致性记录和完整 manifest 条目而临时解除冻结；它现在重新成为冻结的三件套。这是修正演示中不完整的归档流程，不是允许日常修改归档内容。

## 考虑过的替代方案

**以英文为权威、中文仅作辅助翻译。** 这样能减少同步工作，但无法演示源仓库的同等权威约定。

**只增加 `.zh.md` 文件。** 如果没有一致性记录，后续修改可能只更新一种语言而不被发现。只检查文件存在弱于确认内容一致。

**只翻译新 Note。** 这会让当前规则分裂为双语记录和仅英文记录，读者必须记住迁移分界，归档示例的结构也仍然错误。

**复制 DeepSeek Harness 的完整翻译工具链。** 它的合并驱动、快照引用、结构签名、术语库和生成器解决的是大型仓库问题。演示项目需要相同约定和更小的校验器，不需要复制整套生产实现。

**永久冻结归档英文文件，并在外部增加中文说明。** 这样保留了当前 hash，但违反完整归档三件套规则，也把等价历史拆到了互不关联的位置。

## 验证

- 全部七组 Agent Note 都有 `.md`、`.zh.md` 和 `.i18n.yaml` 同目录文件。
- 中英文文件具有双向语言切换行、匹配的生命周期状态，以及等价的必需章节、链接和代码块。
- 每份一致性记录都包含两种语言文件当前的 Git blob hash。
- 修改任一语言而不刷新确认记录时，`npm run verify:notes` 失败。
- 缺失或孤立的配对文件会使验证失败。
- 生命周期重复主题检查以不带语言后缀的主题 stem 为单位。
- 已归档 remove Note 会冻结三个文件，并拒绝任一语言或一致性记录中的单字节改动。
- `npm run check` 报告七组 Agent Note 配对、编译严格 TypeScript 程序，并通过全部十八项行为测试。

## 后果

读者和 Agent 可以使用任一种语言作为同等权威的决策来源，生命周期操作也无法静默遗漏一种语言。语义翻译质量仍由人工评审负责；hash 和结构一致不能证明含义等价。迁移一份已经冻结的演示 Note 是一次例外纠错，不能成为改写归档历史的通用途径。维护两份同等权威文本会增加评审成本，而这个刻意保持简洁的校验器不会复制生产仓库全部的合并与结构检查。
