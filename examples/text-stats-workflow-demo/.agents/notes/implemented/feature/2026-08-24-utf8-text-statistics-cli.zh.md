# Agent Note：UTF-8 文本统计 CLI

Status: implemented

[English](2026-08-24-utf8-text-statistics-cli.md) | 中文

## 问题

用户需要一个小型本地命令，在不打开编辑器、也不把文件内容发送到外部服务的情况下汇总文本文件。行数、词数和字符数看似简单，但结果依赖输入编码、Unicode 字符、空白字符、空文件、末尾行分隔符、输出稳定性和文件失败等明确决策。

项目还需要一项真实功能，用来完整演练从双语提案到实施和人工验收的 Agent Note 工作流。

## 决策

项目提供名为 `text-stats` 的 Node.js ESM 命令，调用方式为：

```text
text-stats <file>
```

命令只接受一个文件路径，并以 UTF-8 读取该文件。缺少参数、参数过多、路径不存在，或者路径无法作为普通文件读取时，以非零状态退出，并在 stderr 输出简洁错误。失败调用不会创建或修改文件。

命令恰好输出三行：

```text
Lines: <count>
Words: <count>
Characters: <count>
```

字符按 Unicode code point 计数，因此补充平面 emoji 算一个字符，而不是两个 UTF-16 code unit。词是由一个或多个 Unicode 空白字符分隔的最大非空序列。本方案有意不做语言学分词：没有空白的连续中文文本算一个词。

行是逻辑文本行。空文件为零行。LF 和 CRLF 都是行分隔符；末尾分隔符结束前一行，但不会额外创建一个空行。中间的空白行仍算一个逻辑行。字符数包含解码文件中的所有 code point，包括行分隔符；因此 CRLF 贡献两个字符。

实现将纯文本计数、文件访问和 CLI 进程行为分离。项目只使用 Node.js 标准模块和 Node 内置测试运行器。`countText` 负责确定性的字符串语义，`countFile` 负责普通文件验证和 UTF-8 读取，`runCli` 负责参数与 stdout，可执行入口负责 stderr 和退出状态。

## 考虑过的替代方案

**读取标准输入。** 这样支持管道，但会引入空流和交互等待语义。单个文件路径让首版范围保持明确；stdin 可以另行提出。

**同时支持文件和 stdin。** 这样更方便，但会在任何一种路径验证需求前引入来源优先级和 `-` 哨兵问题。

**使用 `Intl.Segmenter` 统计词。** 它提供语言学分词，但需要 locale 和运行时数据决策。Unicode 空白 token 具有确定性，也容易解释。

**统计 UTF-16 code unit。** JavaScript 的 `string.length` 成本低，但会把许多 emoji 报告为两个字符，不符合用户对字符计数器的通常预期。

**将行数定义为分隔符数量加一。** 这会让空文件变成一行，并在末尾换行后增加一个空行。逻辑行能提供更实用的文件摘要。

**输出 JSON。** JSON 更便于程序消费，但首版是面向人的命令，并且只有三个稳定值。机器输出仍是独立功能决策。

## 验证

`npm run check` 验证一组双语 Agent Note、编译严格 TypeScript 程序，并通过十二项 Node.js 测试。五项纯函数测试覆盖空文本、Unicode 空白、补充平面 emoji、LF 和 CRLF 逻辑行、中间空白行、末尾分隔符和中文 token 行为。三项文件测试覆盖 UTF-8 成功、路径缺失、目录拒绝以及失败时不创建文件。三项 CLI 测试覆盖固定输出、参数缺失和过多时无 stdout、真实构建子进程、缺失文件 stderr 和退出码 1；一项基础设施测试确认测试运行器。

第一次聚焦运行发现测试手工把 `hello\t世界 😀\n` 计算成十二个 code point，而实现正确返回十一。修正测试值后，五项纯计数测试全部通过，才继续文件和 CLI 工作。最终完整检查通过全部十二项测试。

## 后果

用户可以用确定性的行数、空白 token 数和 Unicode code point 数检查本地 UTF-8 文件，无需外部服务或运行时依赖。纯计数层可以脱离文件系统和进程行为直接复用与测试。

固定的人类可读输出不是版本化机器接口。Unicode 空白 token 具有确定性，但对通常不使用空格书写的语言不具备语言学准确性。Node.js 的 UTF-8 解码会替换畸形字节序列，而不是拒绝。完整读取文件会限制超大文件适用性，Windows 权限行为仍由宿主文件系统决定。
